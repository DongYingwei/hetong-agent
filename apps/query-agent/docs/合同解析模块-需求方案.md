# 合同解析模块 · 需求方案

> 版本:v1.0(草案) · 生成日期:2026-08-11
> 归属:经小管合同管理智能体 · 数据分「合同模块」与「订单模块」,本方案针对**合同模块**。
> 本文档只定义需求与技术方法,不含具体实现代码。

---

## 1. 模块目标

把**合同文件**(PDF / PDF 扫描件)解析为 Markdown,并从中提取合同台账(V2)所需字段,经人工核对后入库,供上层「经小管」查询智能体检索使用。

**一句话职责**:`合同文件 → Markdown → 提取字段 → AI 关键词检测 → 写草稿区 →(人工核对)→ 写正式库`。

---

## 2. 职责边界(已确认)

本模块**端到端负责**:解析 + 字段提取 + 关键词检测 + 入库。整条 ETL 链都在本模块内。

- ✅ 输入:合同 PDF / PDF 扫描件
- ✅ 输出:正式库中一条经人工核对的结构化合同记录 + 4 模块原文(供未来原文检索)
- ❌ 不负责:查询问答(那是 CoreMind 查询 Agent 的事,通过共享数据库解耦)
- ❌ 不负责:订单模块(另有模块)

---

## 3. 输入规格(已确认)

| 项 | 规格 |
|---|---|
| 文件格式 | PDF、PDF 扫描件(合同模块仅此两类;图片/压缩包属订单模块,本方案不含) |
| 扫描件质量 | **基本都是清晰扫描件**,不做倾斜矫正等图像预处理;但仍保留 `md_content` 为空的失败兜底(见 §8) |
| 单份 / 批量 | 两种运行形态都要(见 §9) |

## 4. 解析层:MinerU(已探明的真实接口)

- 接口:`POST http://192.168.121.33:8000/file_parse`
- 参数:`files=@x.pdf`、`backend=vlm-http-client`、`server_url=http://192.168.121.33:18080`
- **同步返回**,无需轮询。响应 JSON 含 `task_id / status / error / results`。
- **Markdown 取值**:`results.<文件名去扩展名>.md_content`
- **成功判定**:`status == "completed"` 且 `error is None` 且 `md_content` 非空
- 超时:合同可能多页,`timeout` 给足(建议 ≥300s)

## 5. 字段提取层(已确认:LLM structured output + Pydantic)

### 5.1 方法
- **输入**:MinerU 产出的 **MD 全文**(不切块,防字段被切断漏抽)
- **抽取**:LLM structured output + Pydantic schema,**按台账 6 大类分组抽取**(不一次抽 20 个字段),**4 模块长文本单独抽**
- **不引入 LlamaIndex**:单份合同全文可进上下文,是结构化抽取问题,不是检索问题

### 5.2 提取范围(照台账"填写方式"分工)
只提取 **20 个 AI 列**;手工列(合同号/考核线/中标编号/关联主合同号/框架简称/合同状态)不提取;系统自动列(断档预警)由系统按到期时间算。

## 6. 模块切分 + 段内 AI 关键词检测(核心难点,已定型)

参照原型「合同模块」:每个模块配置**"对应合同内模块名称"(章节锚点)** + "AI 如何识别该模块(按标题章节归类)"。

### 6.1 流程
```
① 模块切分:AI 按配置的"对应合同内模块名称"(章节锚点),从合同定位并切出 4 段原文
             → mod_service / mod_tech / mod_role / mod_staff
② 段内检测:每个模块段落【各自独立】去精确匹配 AI 关键词表(台账「AI业绩关键词」60词)
③ 模块级结果:每模块记 命中(0/1) + 命中词 + 命中大方向
④ 合同级汇总:tag_ai = 4 模块任一命中
```

### 6.2 检测方法
- **确定性精确子串匹配**(不用 LLM、不用向量),词表 60 词、合同数百份,性能无压力
- 词表结构 `大方向→具体技术`(10 大方向,如"大模型与生成式AI"→大模型/LLM/AIGC…):匹配具体词后反查其大方向

### 6.3 模块级字段(每模块一套)
| 字段 | 说明 |
|---|---|
| mod_service_ai / mod_tech_ai / mod_role_ai / mod_staff_ai | 该模块是否命中 0/1 |
| mod_service_kw / … | 命中的具体关键词(逗号分隔) |
| mod_service_cat / … | 命中词所属大方向 |
| tag_ai | 汇总:任一模块命中即 1(对应台账第26列) |

> 价值:支撑细粒度查询,如"服务内容涉及AI的合同"`WHERE mod_service_ai=1`、"岗位要求AI技能"`WHERE mod_role_ai=1`。

### 6.4 切分锚点【已定:全局一套 + AI 容忍变体】
所有合同共用一套模块定义(4 个模块 + 各自"对应合同内模块名称"),靠 AI 容忍章节名变体("服务内容"可能叫"项目范围""服务标的")。配置简单,与原型一致。

## 7. 入库层:草稿区 → 人工核对 → 正式库(已确认全字段人工核对)

> 数据库【已定:PostgreSQL】。草稿区与正式库同库分表(如 `contracts_draft` / `contracts`),便于事务与一致性。

### 7.1 两阶段数据
- **草稿区**:AI 解析产出的候选,`confirmed=0`。查询 Agent **不查草稿区**。
- **正式库 `contracts`**:人工核对通过后写入。**查询只查正式库 → 入库数据全部有人工背书**,这是 >90% 准确率的核心保障。

### 7.2 字段留痕
每个 AI 字段建议留:
- `<field>`:核对后最终值
- `<field>_ai_raw`:AI 原始候选(供比对与审计)
- 记录级:`confirmed(0/1)` + `confirmed_by` + `confirmed_at`

### 7.3 核对粒度【已定:整份合同级】
人工打开一份合同,一次核完 20 个 AI 字段并确认。记录级 `confirmed(0/1) + confirmed_by + confirmed_at`。

### 7.4 存储策略【已更新:向量库纳入首版,见 §7.6】
- 短结构化字段 → PostgreSQL `contracts`
- 长文本原文(4 模块 + 结算条款/保证金退还/仲裁)→ **存 PG 的 TEXT 列**,保底与审计用
- ⚠️ **决策变更(2026-08-11)**:原"向量库首版不做"已推翻。语义检索(RAG)纳入首版,向量库=Milvus,片段在解析阶段持久化并建向量——详见 **§7.6**。依据见查询侧 [向量检索与RAG问答需求方案](./经小管查询智能体-向量检索与RAG问答-需求方案.md) 与 ADR-0003。

### 7.6 全文分段片段持久化 + 建向量【新增,已授权】

> 触发原因:查询智能体需求升级——支持特定合同细节问答、单合同追问、语义检索。向量化范围=**合同全文**(非仅 7 类长文本字段)。MinerU 解析后即可获取整份合同带格式的完整分段片段,在解析阶段现成,故由**解析侧**产出并持久化。

**7.6.1 片段来源**
- MinerU `md_content` 是带格式的结构化 Markdown → 解析后**就地获取全部分段片段**,不重解析。

**7.6.2 切分策略(结构感知)**
- 先按结构(章节/字段来源)切"父块",超长再按条款/段落二次切;**重叠 1–2 句**防条款被切断。
- **四模块(服务内容/技术要求/岗位说明/人员需求)单独存储**——支撑细粒度检索与按模块粒度增量更新。

**7.6.3 片段 metadata(每片)**
| 字段 | 说明 |
|---|---|
| `contract_id` | 关联正式库合同,供回 PG JOIN/统计 |
| `contract_no` | 合同号,供出处标注 |
| `field` | 来源字段/章节(如 settlement_terms / mod_service / 前言) |
| `module_category` | 命中的 AI 大方向(若属四模块) |

**7.6.4 建向量与写库**
- embedding = **qwen3-embedding-4B**(本地),向量库 = **Milvus**(本地独立部署)。
- **时机**:合同经人工核对入正式库后建向量(与"查询只读已背书数据"一致);草稿区不建向量。
- **归属**:片段产出 + embedding + 写 Milvus 全在解析侧;查询智能体纯只读消费。

**7.6.5 片段同步(一致性命门)【已定:须及时同步】**
| 变更源 | 同步动作 |
|---|---|
| 标签更新(如 `mod_service_ai` 0→1) | 更新 Milvus 对应片段的 metadata,**无需重算向量** |
| 原文更新(重核对/换扫描件) | 对应片段向量 + metadata 重建 |
| 四模块独立存储 | 按**模块粒度增量重建**,不必整份合同重跑 embedding |
- 一致性判据:查询命中片段的 metadata 必须与正式库当前值一致,不得用过期标签过滤。
- 具体同步机制(事件触发 / 批量重建 / 版本号比对)在实现阶段设计。

### 7.5 【重要】查询侧口径规则(写进查询 Agent 的 schema skill)
- **金额可空**:`SUM(amount)` 必须 `WHERE amount IS NOT NULL`;"无金额合同"是合法查询类别
- **金额属性口径**:上限/预估/固定三种混加会失真,求和默认按上限金额或声明口径
- **税率是文本**:不能数值运算

## 8. 失败与低质量处理【已定:标记待人工,不中断批处理】

| 情况 | 处理 |
|---|---|
| 解析失败(加密/损坏) | 进度表记 `failed` + 原因,批处理继续跑其他 |
| md_content 为空(扫描太糊/空白) | 记 `failed`,当解析失败,不当"无内容合同" |
| 字段抽不到 | 该字段留空进草稿,标注供人工补 |
| 人工核对不通过 | 退回草稿,不入正式库 |

> 单份失败不阻断整批;失败集事后人工处理。

## 9. 运行形态(已确认:两者都要)

1. **批处理脚本**:命令行跑一个目录/一批文件,处理存量几百份合同。进度表(SQLite 表或 JSONL)记 `文件→状态(done/failed/pending)+task_id+错误`,支持**断点续跑**(重启只处理 pending/failed)。
2. **常驻服务(HTTP API)**:上传单份合同即时解析,处理持续新增合同。
3. 两者共用同一套解析/提取/入库核心逻辑,只是入口不同。

### 9.1 去重/幂等【已定:按文件内容指纹去重】
- **文件内容指纹**(如 SHA-256)在**解析前**就能算出 → 能提前拦截"同一文件重传",不必等 AI 抽出 contract_no。
- 进度表以指纹为主键:指纹已处理过则跳过/覆盖草稿,不重复解析、不重复入正式库。
- 注意:文件指纹变了(如换扫描版、加了批注)会视为新文件;若同一合同的不同扫描件都要归一,需再叠加 contract_no 作为业务去重(首版先按文件指纹)。

## 10. 与整体架构的关系

```
【合同解析模块】(本方案,独立 Python,批处理+API)
   PDF → MinerU → MD(带格式分段片段) → LLM分组抽字段 → 模块切分+关键词检测
        → 草稿区 →(人工核对)→ 正式库 contracts(SQL 字段 + 原文)
        └─(§7.6)→ 持久化完整分段片段 + qwen3-embedding → 写 Milvus
                              │                              │
                              ▼ 共享 PostgreSQL              ▼ 共享 Milvus
【经小管查询 Agent】(CoreMind 单 Agent,已有 jinguan-qa/)
   自然语言提问 → 自主编排:
     ├ sql_query (只读 Text-to-SQL)                    → Markdown 表格
     ├ vector_search (Milvus 召回50 → reranker 精排8)  → RAG 原文答案(带出处)
     └ 联动: vector_search 返 contract_ids → sql_query  → 统计表格
```

- 解析模块与查询 Agent **解耦**,耦合点=**共享 PostgreSQL + 共享 Milvus**。
- 语义检索(RAG)纳入首版;片段一入库即建向量,查询侧全程只读。
