# 多步规划保持"提示词级 ReAct",不引入引擎级 Planner；结构化结果导出在前端

## 背景

用户要求"不限制提问方式,保留多步规划能力"。这句话有两种截然不同的落法,成本差异巨大:

- **提示词级 ReAct(现状)**:`coremind.yaml` 的 systemPrompt 自称 "Query Planner",在**单回合**内自主选路(SQL / RAG / 语义路由)、串行联动(向量→SQL)、自纠错重试(≤2 次)。CoreMind 本无独立 Planner 组件,规划全靠这段提示词 + ReAct 循环。已建成并验证(T05–T08)。
- **引擎级规划状态机**:CoreMind 0.3.x 的 `loop.planning`(xstate"规划→执行→验证→修复"相位),支持跨回合子问题分解、引擎级重复检测与硬保证。

用户给出的全部真实提问例子——"服务内容含 AI 智能体的合同数/编号/总额"(R1/R5)、"合同 xx 违规怎么处理"(R4+R2)——**都是单路径或"向量→SQL 两步串行",提示词级 ReAct 已完全覆盖**,无一需要引擎级规划。

同一轮还确认了一项新能力:结构化结果**导出 Excel**。

## 决策

1. **多步规划保持提示词级 ReAct,不引入引擎级 Planner**,本次**不升级 CoreMind**(维持 `vendor/coremind` 的 `0.2.0-rc.1`)。引擎级 `loop.planning` 是不可逆升级,在缺乏"单回合串行确实做不到"的真实需求前不采纳。
2. **结构化结果导出放在前端**:网关照常返回 `tableData`(JSON),前端用已装的 `exceljs` 生成 .xlsx 下载。**不新增 Agent 工具、不新增网关路由**。
3. **导出忠实原表**:Excel 内容与 Agent 返回的表逐行一致,**导出层不做任何二次聚合**;尤其不得跨 `amount_type`(上限/固定/预估)合计——"总金额"须由 Agent 在 SQL 侧按口径给出,导出照搬(承接 ADR-0002 与 D4)。

## Considered Options

- **提示词级 ReAct(选定)** vs **引擎级 Planner**:选前者。后者表达力更强,但需不可逆升级 CoreMind 到 0.3.x + 重构 `coremind.yaml` 为 `loop:` + 重跑 28+40 测试防回归,且撞两条硬纪律——坑7(禁同轮并发两工具)、坑10(eval 不支持多轮 turns)。用户例子无一需要它,上它是拿已验证的确定性纪律换一个尚未出现的需求。留作未来增强候选(见"未决")。
- **导出层次:前端(选定)** vs 网关 vs Agent 工具。选前端——`apps/web` 已装 `exceljs`,导出是"把屏幕上的表另存 xlsx"的纯展示动作。网关导出仅在结果超大/需服务端模板时才值得;Agent 工具导出会产生文件副作用,违只读语义(D1)并触碰坑7/坑13,排除。
- **导出是否再合计:忠实原样(选定)** vs 底部加总计行。加总计会把混口径合一,直接违 D4,排除。

## Consequences

- **验收纪律不变**:导出不引入新的数值口径,Q4/Q7 的"数值可核验"由 D3 透明(SQL 折叠框 / 出处三要素)+ 人工抽检守住;数值真值 gate 仍待 G4 标注集(未决)。
- **架构零扩张**:查询侧仍是单 Agent + 两只读工具 + 串行,坑7/坑10/坑13/坑14 的边界全部保留。
- **升级窗口留档**:若未来出现"对比多份合同""跨子问题聚合"等单回合串行做不到的提问,再评估引擎级 Planner + CoreMind 0.3.x 升级(五点五节评估已备),届时须先解决与坑7/坑10 的共存,并新开 ADR 覆盖本条。
