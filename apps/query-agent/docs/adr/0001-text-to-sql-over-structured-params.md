# 查询工具采用 Text-to-SQL 而非结构化过滤入参

现有 `sql_query.ts` 脚手架用结构化入参（`{aggregate, filters}`），注入面小但表达力受限，无法覆盖需求 §4.1/§4.2 的语义时间转换与跨维度拆解（如"服务内容含 AI 但技术要求未提"）。我们决定改为让模型直接生成 SQL，由 `assertReadOnly` 做真正的语句级只读校验。

## Considered Options

- **结构化入参**（现状）：注入面小、易评测，但每新增一种查询维度都要改工具签名，且做不了自由组合的模块级过滤——与"经管专家"的开放式问答目标冲突。
- **Text-to-SQL**（选定）：表达力足以覆盖 4 模块细粒度 + 语义时间；代价是注入风险,由三道只读防线（语句校验 + LIMIT/超时 + 只读账号）承接。

## Consequences

- `assertReadOnly` 从空桩变为**必须实现**的真解析：仅允许单条 SELECT，拒绝多语句/写操作/注入。
- 评测重心从"入参正确"转为"生成的 SQL 语法与业务口径正确"（见 ADR-0002 与 evals）。
- 部署前置：正式库必须用**只读角色**连接，作为最终兜底。
