# 语义检索采用 Milvus + qwen3 两阶段架构，片段由解析侧持久化

需求从"向量库首版不做"升级为"要"：查询智能体需支持特定合同细节问答、单合同追问、跨库语义检索。基于本地现成设施，我们决定用独立 **Milvus** 作向量库、**qwen3-embedding-4B** 做召回、**qwen3-reranker-4B** 做精排的两阶段检索；分段片段在**解析阶段**由 MinerU 产出后持久化并建向量，查询智能体只读消费。

## Considered Options

- **向量库 pgvector（同 PG 一库）** vs **独立 Milvus**：选 Milvus——本地已部署，规模/标量过滤/性能强于扩展；`contract_id` 跨库靠"Milvus 返回 id → 回 PG JOIN 统计"衔接，恰好复用现有 `vector_search` 只返回 id 的契约。
- **单阶段向量召回** vs **两阶段召回+精排**：选两阶段——qwen3-reranker 现成，交叉精排显著提升中文长文本相关性，直接服务 >90% 准确率与"不幻觉"。召回 top_k=50 → 精排 top_n=8。
- **片段归属查询侧自建** vs **解析侧持久化**：选解析侧——MinerU 阶段完整分段片段现成，入库即建向量符合"解析负责写、查询只读"的既定边界（§10）。**此选项使本次工作跨越解析模块，已获用户对解析模块改动的授权。**

## Consequences

- **模块边界扩展**：解析模块新增一步——持久化 MinerU 完整分段片段（四模块**单独存储**）并建向量。查询智能体保持纯只读消费。
- **片段同步**：解析侧标签/原文更新时，向量库对应片段须及时同步；四模块独立存储支持按模块粒度增量重建，不必整份重跑。此一致性是长期正确性命门，须有机制保障（见需求方案）。
- **联动**：Milvus 返回 `contract_id/片段` → 回 PG 做 SQL 统计或直接进 RAG 生成，二选一由 Agent 按提问自主判断。
