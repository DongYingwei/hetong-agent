# Spec S3 · 解析侧全文片段持久化 + 建向量

> 状态：草案（本地，未发布） · 触发标签建议：`ready-for-agent`
> 关联：ADR-0003；上游需求 [合同解析模块需求方案 §7.6](../合同解析模块-需求方案.md)
> 依赖：无（S3 是 S2 的数据前置） · 运行时：**Python 解析模块**（非 CoreMind/TS）

## Problem Statement

查询智能体的语义检索（S2）需要合同全文的分段片段与向量，但当前解析模块只把 7 类长文本存进 PG TEXT 列，未持久化完整分段片段、也未建向量。同时标签会后期更新，若向量库不同步就会用过期数据检索。需要解析侧在 ETL 时产出并持久化全文片段、建向量，并保证更新时及时同步。

## Solution

从用户/系统视角：合同经 MinerU 解析、人工核对入正式库后，解析侧自动把整份合同的分段片段（带 metadata）持久化并写入 Milvus 向量库；四模块片段单独存储；当标签或原文变更时，向量库对应片段及时同步。查询智能体只读消费这些片段与向量。

## User Stories

1. 作为系统，我想在 MinerU 解析后就地获取整份合同带格式的完整分段片段，无需重解析。
2. 作为系统，我想对片段做结构感知切分（按章节/字段切父块，超长按条款切，重叠 1–2 句防切断），以提升检索质量。
3. 作为系统，我想把四模块（服务内容/技术要求/岗位说明/人员需求）片段**单独存储**，以支撑细粒度检索与按模块增量更新。
4. 作为系统，我想每片带 `{contract_id, contract_no, field, module_category}` metadata，以支撑混合检索与出处标注。
5. 作为系统，我想在合同**人工核对入正式库后**才建向量（草稿区不建），以与"查询只读已背书数据"一致。
6. 作为系统，我想用 qwen3-embedding-4B 生成向量、写入 Milvus。
7. 作为系统，当某片段的标签更新（如 `mod_service_ai` 0→1）时，我想只更新 Milvus 对应片段的 metadata，无需重算向量。
8. 作为系统，当原文更新（重核对/换扫描件）时，我想重建对应片段的向量 + metadata。
9. 作为系统，我想按模块粒度增量重建，不必整份合同重跑 embedding。
10. 作为系统，我想保证查询命中片段的 metadata 与正式库当前值一致，不得用过期标签过滤。
11. 作为系统，片段持久化/建向量失败时，我想不阻断整批（沿用解析模块失败即标记待人工的既定策略）。

## Implementation Decisions

- **模块**：解析模块（独立 Python）新增"片段持久化 + 建向量"步骤，接在"人工核对入正式库"之后。（解析方案 §7.6）
- **片段来源**：MinerU `md_content`（带格式结构化 Markdown）解析后就地取全部分段片段。
- **切分**：结构感知——先按章节/字段来源切父块，超长按条款/段落二次切，重叠 1–2 句。四模块单独存储。
- **持久化**：分段片段落库（PG `contract_chunks` 表或等价结构）+ 写 Milvus；metadata = `{contract_id, contract_no, field, module_category}`。
- **建向量**：embedding = qwen3-embedding-4B（本地）；向量库 = Milvus（本地独立）；时机 = 核对入正式库后。
- **片段同步**（一致性命门）：标签更新→仅改 metadata；原文更新→重建向量+metadata；四模块独立→按模块增量。具体机制（事件触发/批量重建/版本号比对）实现阶段设计。
- **失败处理**：沿用解析模块 §8——单份失败标记待人工、不阻断整批。

## Testing Decisions

- **好测试**：只测外部行为——"解析一份合同"函数边界：给定一份 MinerU 输出 → 断言持久化的片段集 + metadata 正确、向量写入被调用；用 fake/记录式 Milvus 客户端断言，不打真向量库、不打真 embedding 服务。
- **接缝（新增，1 个）**：解析侧"处理一份合同"的函数边界（最高可测点）。这是全工作唯一必须新增的接缝——解析模块当前无对应测试基建。
- **需覆盖**：切分产出符合结构感知规则（父块/重叠/四模块独立）；metadata 四字段齐全正确；核对前不建向量、核对后建；标签更新只改 metadata；原文更新触发重建。
- **Prior art**：无同类，属新增接缝；参照解析模块既有的批处理/进度表测试风格（若有）。

## Out of Scope

- 查询侧检索、RAG、路由（→ S2）。
- 结构化字段抽取本体（解析模块既有范围，非本 spec）。
- Milvus collection schema、embedding 维度、索引类型（实现阶段定）。
- 片段同步的最终机制选型（实现阶段设计，本 spec 只定"必须及时同步"的验收判据）。

## Further Notes

- 本 spec 落在解析模块（Python），与 S1/S2（TS/CoreMind）不同运行时——排期时注意跨运行时协作与共享 Milvus 的连接约定。
- 已获用户对解析模块改动的授权（Q10）。
