# Spec S1 · 结构化查询（Text-to-SQL）

> 状态：草案（本地，未发布） · 触发标签建议：`ready-for-agent`
> 关联：CONTEXT.md、ADR-0001、ADR-0002；上游需求 [查询智能体模块需求方案](../经小管查询智能体模块%20·%20需求方案.md)
> 依赖：无（S1 是 S2 的地基）

## Problem Statement

用户想用自然语言问合同库的统计问题（"2026 年签订的运维合同有哪些"、"电力行业含 AI 的合同金额是多少"），但现有 `jinguan-qa/` 脚手架的数据字典与解析模块的真实台账不对齐（缺全部四模块细粒度列），且工具用结构化入参、表达力不足以覆盖语义时间与跨维度组合查询。用户要的是一个能诚实、准确（>90%）地把提问翻译成只读 SQL 并汇总成表格的"经管专家"。

## Solution

从用户视角：向经小管提任意合同**统计类**问题，得到一张 Markdown 表格与数值答案；能查的如实查、口径清晰标注，查不了的诚实说明范围，绝不编造。底层由 Agent 生成只读 SQL（Text-to-SQL），经三道只读防线执行于正式库 `contracts`，报错自纠错、空结果只提示。

## User Stories

1. 作为经管用户，我想问"某年/某季度/上半年签订的合同"，以便按签约时间统计——Agent 依物化时间列语义自行推理该用 `sign_year/sign_quarter/sign_half`。
2. 作为经管用户，我想按行业、合同类型、AI/通信标签过滤，以便做维度统计。
3. 作为经管用户，我想按四模块细粒度过滤（"服务内容含 AI 但技术要求未提"= `mod_service_ai=1 AND mod_tech_ai=0`），以便定位特定合同。
4. 作为经管用户，我想要"数量/总金额/编号列表"三类统计动作，以便覆盖常见问法。
5. 作为经管用户，当我不指定年份时，我想 Agent 默认按当前年并**在输出末尾声明该假设**，以免误解。
6. 作为经管用户，当结果集混含多种金额口径（上限/固定/预估）时，我想 Agent **分口径分组求和并分行标注**，而非隐式相加，以免失真。
7. 作为经管用户，我想 `SUM(amount)` 自动排除无金额合同（`WHERE amount IS NOT NULL`），且"无金额合同"本身是可查询类别。
8. 作为经管用户，当我问的维度不在表结构内（付款进度、履约状态、法律解读等），我想 Agent 诚实说超范围、不臆造列名或数字。
9. 作为经管用户，当我问的不是合同查询（闲聊/常识），我想 Agent 礼貌说明只负责合同库查询。
10. 作为经管用户，我想有"查看 SQL"折叠框，以便专业校验、增加信任。
11. 作为经管用户，当 SQL 执行报错时，我想 Agent 自动重读 schema、改写重试（上限 2 次），仍失败则如实报错。
12. 作为经管用户，当查询结果为空时，我想 Agent 明确提示"未检索到满足条件的记录"，并可建议放宽哪个条件，但**不自动放宽**。
13. 作为管理员，我想查询工具对 `contracts` 仅有 SELECT 权限，且数据库连接用只读账号兜底，以保证正式数据安全。

## Implementation Decisions

- **模块**：重写 `jinguan-schema` skill（数据字典）；改写 `sql_query` 工具（结构化入参 → 裸 SQL + 真 `assertReadOnly`）。（ADR-0001）
- **schema skill 内容**：列出查询可用子集——结构化字段 + 四模块 `mod_*_ai/kw/cat` + 物化时间列（`sign_year/quarter/half`、`end_year`）；长文本原文列标注"仅存在性过滤（IS NOT NULL/LIKE），不 SELECT 全文回灌"；排除手工列/系统计算列。字段口径以解析模块 §5.3 的 29 字段台账为准。
- **只读三防线**（ADR-0001）：① `assertReadOnly` 真解析（仅单条 SELECT，拒绝写操作/多语句/注入）；② 强制 LIMIT + 语句超时；③ PostgreSQL 只读角色连接（部署前置，`/wizard` 阶段提供连接串）。
- **金额纪律**（ADR-0002）：`SUM(amount)` 带 `WHERE amount IS NOT NULL`；跨 `amount_type` 分组求和不合一；税率 TEXT 不做数值运算。
- **语义时间**（ADR-0002）：schema 只声明物化列语义，不做"说法→条件"固定映射表；由 Agent 检索时推理。删除现有 schema skill 的旧映射表与"严禁自行推理"表述（二者矛盾）。
- **当前日期注入**：运行前替换 systemPrompt 日期占位（yaml 已注释此约束），纳入部署脚本。
- **自纠错**：借 CoreMind assisted 循环，报错重试上限 2 次；空结果只提示不放宽。
- **能力边界**：超范围/非合同查询诚实拒答，不臆造。

## Testing Decisions

- **好测试**：只测外部行为——自然语言输入 → 工具轨迹 + 输出，不测 `sql_query` 内部实现。
- **接缝（复用现有，1 个）**：`coremind eval` 跑 `evals/scenarios.yaml`，从提问到"轨迹+输出"整条黑盒验证。
- **首版 gate**：核心子集（标准三问 + 时间×标签×四模块组合，约 15–20 题）100% 通过 trajectory（纯结构化只调 `sql_query`）+ outcome + SQL 语法/口径正确。**不含数值真值比对**（测试库快照后续建立）。
- **Prior art**：现有 `evals/scenarios.yaml` 的 trajectory/response grader 结构。

## Out of Scope

- 语义/向量检索、RAG、单合同追问（→ S2）。
- 解析侧片段持久化与建向量（→ S3）。
- 数值真值比对与 50/20 全量题库（后续里程碑，需测试库快照真值，由用户提供）。
- 订单模块。

## Further Notes

- 测试库快照真值、只读账号连接串属用户控制项，不由实现方编造。
- schema skill 完整度 = 系统可覆盖的提问范围；每次数据库加列/改语义须同步更新 skill + 增 eval 场景。
